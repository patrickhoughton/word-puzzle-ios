# Phase 5 — UI Design Contract

> Visual and interaction contract for the new Settings screen, the Dynamic Type migration of `GameTheme.swift`, sound-effect feedback, the app icon, and App Store screenshots. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — native SwiftUI (iOS 17.6 target); shadcn/component-registry tooling is React-specific and not applicable to this platform (matches Phase 3/4 precedent) |
| Preset | not applicable |
| Component library | none — native SwiftUI controls only (`Toggle`, `Button`, `VStack`/`HStack`), consistent with CLAUDE.md's "no third-party dependency" guidance |
| Icon library | SF Symbols — `gearshape` (new: Settings entry point) joins Phase 3's `shuffle`/`delete.left`/`checkmark.seal.fill` |
| Font | System font (San Francisco), now via scalable Dynamic Type text styles instead of fixed `Font.system(size:)` literals — see Typography below (D-04) |

**Source of truth:** `WordPuzzle/WordPuzzle/Game/GameTheme.swift` — frozen spacing/color tokens from 03-UI-SPEC.md (approved 2026-08-29) carry forward unchanged. This phase's only change to `GameTheme.swift` is the Typography section (font tokens become scalable), per D-04/D-05. No new spacing or color tokens are introduced.

**Scope note:** Phase 5 adds exactly one new screen (Settings) and one new entry-point control (gear icon). Everything else in this phase is a migration (Dynamic Type), an addition to an existing view (sound calls into existing interaction points), or non-screen production work (app icon, screenshots). This spec covers all of it, organized by workstream.

## Component Geometry — HexTileView Dynamic Type Clamp (D-05)

New for Phase 5 — extends 03-UI-SPEC.md's "Component Geometry" section, does not replace it:

- Hex tile diameter stays fixed at **70pt** (unchanged — D-05 explicitly does not rework `HexFlowerLayout` geometry).
- Hex tile letter glyph switches from a fixed `GameTheme.displayFont` (34pt) to a **clamped `@ScaledMetric`**:
  - Base value: **34pt**, `relativeTo: .largeTitle` (matches the current visual size at the default Dynamic Type category exactly — no visible change at default settings).
  - Clamp ceiling: **40pt** — `min(scaledValue, 40)`. This is the load-bearing mechanism; `@ScaledMetric` has no built-in max parameter (confirmed in RESEARCH.md).
  - Defense-in-depth: `.lineLimit(1)` + `.minimumScaleFactor(0.5)` stay on the `Text` as a fallback, not the primary mechanism.
- Verification requirement: visually check at the largest **accessibility** category (AX5, via Settings > Accessibility > Display & Text Size > Larger Text, not just the standard xxxLarge) that no tile clips or overflows its hexagon — per RESEARCH.md Pitfall 1.

## Typography

**Values change from fixed points to scalable text styles (D-04) — visual size at the default Dynamic Type category is unchanged, but all four now scale with the system setting:**

| Role | Text Style | Weight | Effective size (default category) | Line Height |
|------|-----------|--------|-------------------------------------|-------------|
| Display | `.largeTitle` | semibold (600) | 34px | System-managed (`UIFontMetrics`) — no manual override, same precedent as Phase 3 |
| Heading | `.title3` | semibold (600) | 20px | System-managed |
| Body | `.body` | regular (400) | 17px | System-managed |
| Label | `.footnote` | regular (400) | 13px | System-managed |

Declaration (goes into `GameTheme.swift`, replacing the four `Font.system(size:weight:)` lines):
```swift
static let displayFont = Font.largeTitle.weight(.semibold)
static let headingFont = Font.title3.weight(.semibold)
static let bodyFont = Font.body
static let labelFont = Font.footnote
```

No call sites change — every existing view (`WordDisplayView`, `ScoreBarView`, `MissedWordsView`, `PaywallView`, `GameView`) and the new `SettingsView` reference these tokens by name.

**Exception:** `HexTileView`'s letter glyph does NOT use `GameTheme.displayFont` after this migration — it uses the clamped `@ScaledMetric` value described in Component Geometry above, so the fixed hex tile never clips. This is the only place in the app where a font size is NOT a pure Dynamic Type text style.

**Regression guard:** after migration, `grep -c "Font.system(size:" GameTheme.swift` must return `0`; the only remaining `Font.system(size:` in the codebase should be inside `HexTileView`'s clamp code.

Exactly 4 roles, exactly 2 weights — unchanged from Phase 3, no additional sizes/weights introduced.

## Screen — SettingsView (new, UX-02)

Presentation-only, value-in/closure-out, matching `PaywallView`/`MissedWordsView` convention (zero `@Environment`/store coupling):

```swift
struct SettingsView: View {
    @Binding var soundEffectsEnabled: Bool
    let onDone: () -> Void
}
```

Layout: `NavigationStack` (or a plain `VStack` inside a `.sheet` with an explicit Done button — either is acceptable; Done button is required regardless of container choice) containing:

1. Nav bar / header: title `"Settings"` (Heading-font if custom header, or standard `.navigationTitle` if `NavigationStack` is used).
2. Single row: `Toggle("Sound Effects", isOn: $soundEffectsEnabled)`, Body-font label, `GameTheme.md` padding, `GameTheme.lg` horizontal screen padding, `GameTheme.xxl` top padding below the header.
3. Trailing nav bar item (or bottom button if not using `NavigationStack`): `"Done"` — dismisses the screen via `onDone()`.

**Entry point (Claude's discretion, resolved):** A `gearshape` SF Symbol icon button in `GameView`'s top-trailing safe area, above `ScoreBarView`. `Color.secondary`, 44×44pt tap target via `.contentShape`, `.sheet` presentation (not `.fullScreenCover` — unlike the paywall, Settings is dismissable, so a sheet is the correct presentation style). Accessibility label: `"Settings"`.

No new component library, no new colors beyond the accent-toggle usage documented above.

## Audio Feedback Contract (UX-02, D-01/D-02)

Not a visual element, but a load-bearing interaction contract for this phase — included here since `gsd-planner`/`gsd-executor` need it alongside the visual spec.

| Event | Trigger | Character | File | Format |
|-------|---------|-----------|------|--------|
| Word accepted | Valid word submitted (non-pangram) | Short, bright, single confirmation click/pop — under 300ms | `word_accepted.wav` | 44.1kHz WAV (or converted `.caf`), mono, < 50KB |
| Word rejected | Invalid word submitted | Short, low/soft negative blip — distinct from acceptance, not harsh/alarming (casual game tone) | `word_rejected.wav` | same |
| Pangram found | Submitted word is a pangram | Distinctly bigger/brighter than the plain-accept sound — e.g. a short ascending two-note chime, per D-01's "distinct/bigger than a normal accept" | `pangram_found.wav` | same |
| Round end / paywall shown | Round finishes (`.roundOver` or `.paywalled` phase entered) | Gentle, resolved completion tone — not celebratory-only (must feel neutral enough to also precede the paywall) | `round_end.wav` | same |

- **Source:** Kenney UI Audio pack (kenney.nl/assets/ui-audio, CC0, no attribution required) — download the WAV variant directly (no format conversion needed for `AVAudioPlayer`), per D-02 and RESEARCH.md's environment note.
- **Selection guidance:** pick clips matching the "Character" column above from the pack's click/confirm/error/chime clips; the exact filenames within the downloaded pack are an execution-time choice (subjective audio judgment, explicitly Claude's discretion per CONTEXT.md) — the four characteristics above are the prescriptive contract the choice must satisfy.
- **Playback behavior:** `AVAudioSession` category `.ambient` (mixes with other audio, respects the hardware silent switch) — per RESEARCH.md Pattern 3/Pitfall 3. Never `.playback`.
- **Mute behavior:** when `soundEffectsEnabled == false` (via `@AppStorage`, set from `SettingsView`'s toggle), `SoundManager.play(_:enabled:)` is a no-op — no visual indicator needed elsewhere in the UI beyond the Settings toggle itself (no per-event mute icons).

## App Icon Concept Directions (UX-04, D-08)

Two concepts to draft first (as `ImageRenderer`-exported SwiftUI views per RESEARCH.md's recommended tooling) for Patrick to react to before final 1024×1024 PNGs are produced for the three `AppIcon.appiconset` slots (universal / dark / tinted):

**Concept A — Single hex tile:** One large hexagon (matching `HexagonShape`'s geometry) filling most of the 1024×1024 canvas, gold (`#F5B800`) fill, with a single bold uppercase letter centered inside (e.g. "W" for Word, or a stylized honeycomb "•" motif) in the same `Color.black`-on-gold treatment `HexTileView` already uses for its center tile. Simplest, most legible at small sizes (App Store thumbnail, home screen).

**Concept B — Honeycomb cluster:** A small cluster of 3–7 hexagon tiles (echoing `HexFlowerLayout`'s center + ring composition) arranged as in-game, gold center tile + neutral/secondary-surface outer tiles, on a `Color(.systemBackground)`-equivalent flat background. More literal callback to the in-game hex-flower UI, more visually complex at small sizes — flag legibility risk at 40×40pt (Settings icon size) as part of Patrick's review.

**Slot-specific requirements:**
- **Universal (light):** as designed above.
- **Dark:** same composition; verify the gold/black contrast still reads on a dark system background (iOS may composite the dark variant on a dark backdrop — the icon's own background fill matters more than in light mode).
- **Tinted:** iOS's monochrome tinted mode strips color — verify the composition remains legible as a single-tone silhouette (the hexagon outline/letter shape must carry the design without relying on the gold/black color contrast).

No production PNGs are created by this spec — this section is the concept brief Claude drafts and Patrick reviews before final asset production, per D-08.

## Screenshot Contract (UX-04, D-09)

Captioned marketing screenshots — real Simulator gameplay captures overlaid with short marketing copy and device frames (not plain uncaptioned screenshots), per D-09.

**Device/size scope:** Mandatory 6.9" iPhone size (1320×2868px) captured via `xcrun simctl io booted screenshot` on the iPhone 17 Simulator. iPad screenshots are **not** in scope by default — this spec adopts RESEARCH.md's Open Question 1 recommendation to restrict `TARGETED_DEVICE_FAMILY` to `"1"` (iPhone only), consistent with CLAUDE.md's "Platform: iOS only... for iPhone" framing and Phases 1-4's iPhone-only testing. **This is a default pending confirmation** — if Patrick instead wants iPad support kept, this section's device scope and the icon's iPad-idiom needs would need revisiting before screenshot production.

**Screens to feature (minimum 3, per UX-04):**

| # | Screen | Tagline (marketing copy) |
|---|--------|---------------------------|
| 1 | Mid-round gameplay (hex grid + word display + ScoreBar, several words already found) | `"Endless word puzzles, fresh every round"` |
| 2 | Round-end reveal (`MissedWordsView`, ideally showing a pangram badge) | `"Chase every pangram, track every word"` |
| 3 | Paywall / unlock screen (`PaywallView`) | `"Unlock unlimited puzzles — no subscription, just $2.99"` |

Optional 4th screen (discretion): Settings screen or a second gameplay moment (e.g. a "Legend" rank tier ScoreBarView) — not required to hit the 3-screenshot minimum but adds variety if time allows.

**Caption treatment:** short (under 8 words), Display or Heading-weight equivalent styling in the compositing tool (Keynote/Figma/Preview — no `fastlane frameit` available per RESEARCH.md's environment check), positioned above or below the framed device image, using the app's `#F5B800` gold as an accent on the caption text or background to stay visually consistent with the in-app accent color.

**Copy tone:** matches the app's existing copywriting register (declarative, benefit-first, no exclamation-mark overuse — consistent with in-app strings like `"Perfect Round!"` being the one intentional exception for a celebratory moment, not the baseline tone).
